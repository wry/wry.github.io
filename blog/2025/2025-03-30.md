# 2025-03-30 - Crashing unit tests

I'd had a deadlock issue with unit tests ever since upgrading on my dev box to Xcode 16 last year and with the looming update of Xcode on the build server I decided this weekend to investigate what the root of the problem was.

It looked like [load_images](https://github.com/apple-oss-distributions/objc4/blob/main/runtime/objc-runtime-new.mm#L3719) from the objc runtime was calling a [+load](https://developer.apple.com/documentation/objectivec/nsobject-swift.class/load()?language=objc) in a third party lib, which, seemingly starting with Xcode 16 suffers a deadlock. Initialization in a `+load` is tricky, because, as detailed [here](https://www.mikeash.com/pyblog/friday-qa-2009-05-22-objective-c-class-loading-and-initialization.html) it happens even before `main()`.

## Searching, loading, ready, run

To test and see how +load behaves I quickly wrote and ran this snippet :

```shell
% cat bla.m && clang -framework Foundation bla.m && ./a.out
#import <Foundation/Foundation.h>

@interface Klass: NSObject
@end

@implementation Klass
+(void)load
{
  NSLog(@"load");
}
@end

int main(void)
{
  NSLog(@"main");
  return 0;
}
2025-03-30 14:26:20.092 a.out[18907:260768] load
2025-03-30 14:26:20.093 a.out[18907:260768] main
```

Going back to the iOS stacktrace and now understanding a bit better how `+load` works I wondered if the deadlock had something to do with using those `UIKit` calls this early during launch. Since live patching is cheap if you're already in a debugger, I `mem wr`'d a `ret` in the offending function in the hope that the deadlock would be resolved and lo and behold, the unit tests ran flawlessly. Seeing this, I thought if I could somehow either break or at least defer this `+load` until `-[UIApplicationDelegate application:didFinishLaunchingWithOptions:]`, I could fix the CI/CD pipelines while there's no fix in the third party lib.

Without an active debugging session live patching wasn't much of an option, so I was looking to binary patch the lib, perhaps by overwriting the `load` symbol with a different string of equal length, so as to 'hide' it from the runtime until I can manually call it at a more convenient time, should that be required.

To see how my super elaborate guinea pig would behave under the same circumstances, I decided to patch that as well. First I had to find the location of the method :

```shell
% objdump --macho --section '__TEXT,__objc_methname' ./a.out
./a.out:
Contents of (__TEXT,__objc_methname) section
0000000100003f94  load
```

That offset is with vmaddr, so `0x3f94` offset in the file, but just to confirm :

```shell
% od -t c -N 4 ./a.out 0x3f94
0003f94    l   o   a   d                                                
0003f98
```

To patch it, I used the usual perl/dd combo :

```shell
% perl -e "print pack('c', hex('0x74'));" | dd of=./a.out bs=1 count=1 conv=notrunc seek=$(perl -e "print hex('0x3f94')")
1+0 records in
1+0 records out
1 bytes transferred in 0.000109 secs (9174 bytes/sec)
```

After which I confirmed that my bufonid changeling had overtaken the binary (all hail hypnotoad!) :

```shell
% od -t c -N 4 ./a.out 0x3f94
0003f94    t   o   a   d                                                
0003f98
```

...but running it caused an immediate crash :

```shell
% ./a.out

% echo $?

```

## Sighs and signs

This got me thinking it's some macos level issue. Sometimes these issues resurface through `Console.app`, so I ran that, streamed my dev box log and triggered the crash again. Sure enough, it revealed the culprit straight away :

```shell
CODE SIGNING: process ... rejecting invalid page at address ...(signed:1 ... tainted:1 ...)
```

Searching for a solution hoping it would NOT involve disabling SIP I found [this post](https://developer.apple.com/forums/thread/673057) where according to op running cmd

```shell
spctl developer-mode enable-terminal
```

then enabling `System Preferences / Privacy & Security  / Developer Tools / Terminal` would fix the problem. So I compiled the binary again, patched it again, ran it again... still crashed. I patched it back to its original form and ran it again... crashed again. I checked the binary contents and they were the same. Copying this crashing binary to a new name let me run it, but only the version that was patched back to its original form. After patching the symbol name back to `toad` again, it would crash, whatever filename I tried running it under. I guess that security switch has its limitations... an investigation for another time.

What worked in the end was codesigning it with the ad-hoc signature (`If identity is the single letter "-" (dash), ad-hoc signing is performed.` (codesign(1))) :

```shell
codesign -f -s - a.out
```

Running the new binary worked as expected and the `+load` method was no longer called :

```shell
% ./a.out
2025-03-30 14:30:25.709 a.out[25808:533528] main
```

After this side-quest I went back to the Xcode 16 issue and looking for more information about app/library bundles and code signing I bumped into [this fascinating article](https://developer.apple.com/forums/thread/702351), but after reading up on it and understanding how complex it was, I opted for the much simpler 'trick' that had already worked earlier and used the ad-hoc codesign on the third party lib as well, which now ran all the unit tests just as before.
