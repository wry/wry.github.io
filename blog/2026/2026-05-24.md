# 2026-05-24 - Core Data, NSKeyedArchiver, objc

This past week the topic came up to support a closed source format used by a third party library, even after no longer having access to it. The way the application interacts with this lib is through archived instances stored as binary blobs in Core Data. The problem sounded interesting enough to work on it over the weekend as well.

## Core Data

Core Data is used to abstract away the details of data persistence and on iOS it's usually backed by sqlite, so in order to retrieve the data to inspect it, first we'd want to load the database, then execute an sql cmd with the right table and column arguments.

### Locating the database

If you're using the sim, you can get the data from the sqlite db, as long as you can find out its path. Before you can do that, you need to fire up a sim instance with the app installed on it and find the UDID of the device. You can do that with the one liner :

```shell
xcrun simctl list | grep Booted | awk 'BEGIN{FS="[()]"}{print $4}'
```

Once you know the UDID, you can get the Data path using `simctl appinfo`, eg.:

```shell
xcrun simctl appinfo $(xcrun simctl list | grep Booted | awk 'BEGIN{FS="[()]"}{print $4}') com.example.app | grep DataContainer
```

If your app is called MyApp, the sqlite file used by Core Data will be at that path, suffixed with "/Documents/MyApp.sqlite".

### Getting the data

The command `sqlite3`, at the time of writing, comes preinstalled on macOS, so you can use that to execute sql cmds against the db. `sqlite3` won't display binary data on stdout, so you'll want to either extract it with [writefile](https://sqlite.org/cli.html#file_i_o_functions), or use `hex()`, to convert it to its hexadecimal representation that you can then convert back into bytes using eg. `xxd`.

Core Data stores entities created through its visual editor in tables after prefixing them with `Z` and attributes in columns also prefixed with `Z`. For instance, if your blob is in entity `User` and attribute `data`, you can prepend `Z` to both to get the table and column names and then run the following cmd, if your path to the sqlite file is in env var `$DBPATH` :

```shell
echo "SELECT HEX(ZDATA) FROM ZUSER WHERE ZUSERNAME = 'user' LIMIT 1" | sqlite3 $DBPATH | xxd -r -p > /tmp/data.plist
```

In the cmd above we extracted the data from Core Data as a hex string, converted it back to bytes using `xxd` and stored it all in `/tmp/data.plist`. The filename is a bit of a spoiler - archives are binary plists, you can confim this running `file /tmp/data.plist`.

Once we have the archive, we can display it using `plist` :

```shell
plutil -p /tmp/data.plist
```

## NSArchives

If you've ever archived/unarchived instances, you'll know that all you need to do is implement the protocol `NSCoding`, then implement its two methods that will be called during archiving/unarchiving, passing you the coder instance you can use to encode/decode the values.

An archive is an `NSDictionary` when loaded, with all the data you've archived, including the classnames and class hierarchies of classes that were part of it.

Since the details of our data is only known to the third party lib and the archive makes reference to the classes of that third party library, once we remove the third party lib dependency from the application it will be impossible to unarchive the data in its current form.

## Reconstruction

The main content of an archive is in a field called `$top`, with each encoded property stored as a `CFKeyedArchiverUID` field, with a value that is an index into the `$objects` array where the actual value is stored. Each of these objects - with the exception of the first one - will either be of a base type (eg `4` as `NSNumber*`), a class definition entry or an object with a `$class` field of `CFKeyedArchiverUID` type, that points to an object that has a `$classname` and `$classes` field. Former will have the class name and latter the class hierarchy.

My first approach was to just see if I could even make it load the archive, just by creating fake classes following the naming and class hierarchy shown by `plutil -p`, so I quickly wrote a `main.m` and added code to unarchive the binary plist. This worked and (initWithCoding:)[https://developer.apple.com/documentation/foundation/nscoding/init(coder:)?language=objc] was called, so I figured my next step would be extracting the data from the archives this way, but it kept choking on one of the `-[NSCoder decodeObjectForKey:]` calls - if this call returned a `nil`, no more objects could be decoded. The problem was a `UIColor` instance - since I was not using `UIKit`, it made sense that this class would be missing. Adding a fake class fixed the issue and I could read all of the properties.

I hypothesized that if I could rewrite the classes in the binary archive to my new classes, I'd not have to create separate fake classes just to keep them as containers, so I opened the binary plist to rewrite the classes from code. Running the program triggered the new `NSCoding` methods on the new classes.

As a side note to self, it would have been quicker to rely on `plutil`'s `-convert` arg to convert the bplist to the `xml1` format, edit it and turn it back into the original `binary1` format.

## CFKeyedArchiverUID

Walking an `NSDictionary` instance isn't that challenging, but there is one class that's not defined in any public header: `CFKeyedArchiverUID`. Googling it leads you to (this source)[https://github.com/opensource-apple/CF/blob/master/CFBinaryPList.c], which reveals it as

```c
struct __CFKeyedArchiverUID {
    CFRuntimeBase _base;
    uint32_t _value;
};
```

`CFRuntimeBase` is part of `CoreFoundation` and defined (here)[https://github.com/apple-oss-distributions/CF/blob/main/CFRuntime.h] as 

```c
typedef struct __CFRuntimeBase {
    uintptr_t _cfisa;
    uint8_t _cfinfo[4];
#if __LP64__
    uint32_t _rc;
#endif
} CFRuntimeBase;
```

Since I couldn't import `CFRuntime.h` I just added all the bytes together (both platforms are 64 bit) :

```shell
echo '#include <stdint.h>\n#include <stdio.h>\nint main() { printf("%lu", sizeof(struct {uintptr_t a; uint8_t b[4]; uint32_t c;})); }' | clang -x c - && ./a.out
```

The final struct added to my code was :

```c
typedef struct
{
    uint8_t padding[16];
    uint32_t value;
} AAKeyedArchiverUID;
```

This is not the most reliable approach, but since old iOS versions and newer ones both have to be able to read it, not sure how likely it is that the format would change abruptly.

## Epilogue

Extracting data from an archive is of course just a tiny fraction of the task and the greater part will be supporting the features that relied on all that data, but at least triggering the `NSCoding` methods of my new classes with the persisted data during unarchiving should now work out of the box.

As a reminder for future self, I wrote a q&d prog to generate the source code that could be used to support old data generated with `NSKeyedArchiver`. You can find it as `ardec` in the `snippets` repo.
